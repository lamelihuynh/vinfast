Topic này nói về gì

Tóm tắt

Khi bạn gửi một câu SQL, PostgreSQL không chạy nó "y như chữ". Bộ planner sẽ chọn cách đọc bảng (dùng index hay quét cả bảng) và cách nối bảng (nested loop, hash join, merge join). MongoDB cũng vậy với aggregation pipeline: thứ tự các stage quyết định có dùng được index hay không.

App VinFast giờ có dữ liệu ở 2 nơi: đơn hàng ở PostgreSQL, sản phẩm ở MongoDB. Không thể JOIN giữa 2 DB, nên phải chọn: lưu sẵn tên sản phẩm trong đơn (snapshot), hay ghép dữ liệu ở PHP. T3 viết lại các trang đọc đơn hàng, dashboard admin và thống kê từ log, rồi đo xem cách viết nào nhanh hơn, vì sao.

Sau topic này bạn trả lời được

  • Đọc một EXPLAIN ANALYZE: node nào tốn thời gian nhất, planner ước lượng sai ở đâu.
  • Khi nào planner chọn Nested Loop, Hash Join, Merge Join.
  • Subquery, JOIN, CTE, window function, LATERAL, materialized view khác nhau thế nào về plan và tốc độ.
  • Viết pipeline $match → $group → $sort → $limit → $lookup đúng thứ tự để dùng index.
  • Join trong DB vs join ở PHP vs N+1: tốn bao nhiêu round trip, bao nhiêu ms.
  • Vì sao phân trang OFFSET chậm dần ở trang sâu, keyset thì không.

Planner và EXPLAIN

Planner ước lượng cost cho nhiều cách chạy rồi chọn cách rẻ nhất. Cost là đơn vị tương đối, không phải ms.

EXPLAIN in plan dự kiến. EXPLAIN ANALYZE chạy thật và in thêm thời gian, số dòng thật. Đọc plan từ node thụt sâu nhất ra ngoài.

Ví dụ: lọc orders WHERE user_id = 2 sẽ thấy Index Scan using idx_orders_user_created. Bỏ điều kiện thì thấy Seq Scan on orders.

3 thuật toán join

  • Nested Loop: với mỗi dòng bảng ngoài, tìm dòng khớp ở bảng trong (tốt khi bảng ngoài ít dòng và bảng trong có index). Ví dụ: 10 đơn của 1 user → tìm item theo idx_order_items_order.
  • Hash Join: dựng bảng băm từ bảng nhỏ, quét bảng lớn để dò. Tốt khi nối nhiều dòng, điều kiện =. Ví dụ: toàn bộ orders ⋈ order_items để tính top bán chạy.
  • Merge Join: hai phía đã sắp theo khóa join rồi trộn. Tốt khi cả hai đã có thứ tự (index hoặc Sort).

CTE, window function, LATERAL

CTE (WITH x AS (...)) giúp chia câu dài thành từng bước. Từ PostgreSQL 12, CTE thường được "inline" vào câu chính. Viết AS MATERIALIZED để bắt nó chạy riêng một lần.

Window function tính trên một "cửa sổ" dòng mà không gộp dòng. Ví dụ COUNT(*) OVER() trả tổng số đơn cạnh từng dòng; ROW_NUMBER() OVER (PARTITION BY tháng ORDER BY qty DESC) lấy top 3 sản phẩm mỗi tháng.

LATERAL: subquery bên phải được dùng cột của bảng bên trái. Order.php dùng nó để lấy item đầu tiên của mỗi đơn.

Aggregation pipeline (MongoDB)

Pipeline là một mảng stage, dữ liệu chảy qua từng stage theo thứ tự.

  • $match: lọc (như WHERE). Đặt đầu tiên thì dùng được index.
  • $group: gộp (như GROUP BY).
  • $sort, $limit, $project.
  • $unwind: tách mảng thành nhiều document (mỗi item một document).
  • $lookup: "join" sang collection khác trong cùng DB Mongo. Không join được sang PostgreSQL.

Xem plan bằng db.coll.explain("executionStats").aggregate([...]), tìm IXSCAN (dùng index) hay COLLSCAN (quét hết).

Join khi dữ liệu ở 2 DB

order_items ở PG, products ở Mongo. Có 3 cách hiện tên sản phẩm trong lịch sử đơn:

  1. Snapshot: đọc order_items.product_name_snapshot. 1 DB, ít round trip. Tên là tên lúc mua.
  2. Join ở backend: lấy product_id từ PG, gọi Mongo một lần {productID: {$in: [...]}}, ghép trong PHP.
  3. N+1: mỗi item gọi Mongo một lần. Code ngắn nhưng chậm khi nhiều item.

Phân trang OFFSET và keyset

LIMIT 20 OFFSET 20000 vẫn phải đọc và bỏ đi 20 000 dòng đầu. Trang càng sâu càng chậm.

Keyset nhớ dòng cuối của trang trước: WHERE (created_at, id) < (:last_created, :last_id) ORDER BY created_at DESC, id DESC LIMIT 20. Có index thì tốc độ gần như không đổi theo số trang. Đổi lại, không nhảy thẳng tới trang 500 được.

Mục tiêu: tự tay thấy Nested Loop, Hash Join, Merge Join trên cùng một câu SQL.

Vì sao cần

Đây là nền cho mọi thí nghiệm tuần 5. Trên DB dev chỉ có 3 đơn, planner luôn chọn Nested Loop. Cần dữ liệu 10k để thấy khác biệt.

Các bước

  1. Tạo DB benchmark (lệnh từ bench/README.md): 
    docker compose exec -T postgres createdb -U vinfast vinfast_bench
docker compose run --rm -e MONGO_DB=vinfast_bench mongo-init

  2. Mở psql vào DB đó: docker compose exec postgres psql -U vinfast -d vinfast_bench.
  3. Chạy câu join và ghi lại node join: 
    EXPLAIN (ANALYZE, BUFFERS)
SELECT oi.product_id, SUM(oi.quantity) AS qty
FROM orders o JOIN order_items oi ON oi.order_id = o.id
WHERE o.status <> 'cancelled'
GROUP BY oi.product_id ORDER BY qty DESC LIMIT 10;
  4. Ép planner đổi thuật toán (chỉ trong phiên psql này), chạy lại câu trên sau mỗi lệnh: 
    SET enable_hashjoin = off;   -- thường thấy Merge Join
SET enable_mergejoin = off;  -- giờ còn Nested Loop
RESET ALL;
  5. Thử 3 kỹ thuật khác, mỗi kỹ thuật xem plan: 
    -- CTE: so sánh 2 plan
WITH valid AS (SELECT id FROM orders WHERE status <> 'cancelled')
SELECT COUNT(*) FROM order_items oi JOIN valid v ON v.id = oi.order_id;
WITH valid AS MATERIALIZED (SELECT id FROM orders WHERE status <> 'cancelled')
SELECT COUNT(*) FROM order_items oi JOIN valid v ON v.id = oi.order_id;

-- Window function: top 3 sản phẩm mỗi tháng
WITH monthly AS (
  SELECT date_trunc('month', o.created_at) AS m, oi.product_id,
         MIN(oi.product_name_snapshot) AS name, SUM(oi.quantity) AS qty
  FROM orders o JOIN order_items oi ON oi.order_id = o.id
  WHERE o.status <> 'cancelled'
  GROUP BY 1, 2)
SELECT to_char(m, 'YYYY-MM') AS ym, name, qty, rn FROM (
  SELECT m, name, qty, ROW_NUMBER() OVER (PARTITION BY m ORDER BY qty DESC, name) AS rn
  FROM monthly) t
WHERE rn <= 3 ORDER BY m, rn;
  6. Lưu các câu vào bench/t3/warmup.sql, ghi nhận xét vào bench/t3/README.md.

  • bench/t3/warmup.sql MỚI, bench/t3/README.md MỚI

Kết quả mong đợi / tự kiểm tra

  • Có ghi chép cho cả 3 node: Hash Join, Merge Join, Nested Loop, kèm thời gian Execution Time của mỗi lần.
  • Trả lời được: planner tự chọn thuật toán nào, vì sao, và rows= ước lượng lệch bao nhiêu so với actual rows.
  • Câu window function trả tối đa 3 dòng mỗi tháng.

Lỗi hay gặp

  • Quên -d vinfast_bench nên chạy trên DB dev (chỉ 3 đơn).
  • Quên RESET ALL rồi đo câu khác: kết quả bị sai vì planner vẫn đang bị cấm hash join.
  • Chạy EXPLAIN ANALYZE với câu UPDATE/DELETE: nó chạy thật. Bọc trong BEGIN; ... ROLLBACK;.

public static function findManyByIds(array $ids): array
{
    $ids = array_values(array_unique(array_map('strval', $ids)));
    if (!$ids) { return []; }
    $out = [];
    foreach (self::collection()->find(['productID' => ['$in' => $ids]]) as $doc) {
        $p = self::formatProduct($doc);
        $out[$p['product_id']] = $p;
    }
    return $out;
}

Mục tiêu: hai khối mới trên dashboard: top 10 sản phẩm bán chạy 30 ngày, 10 phiên bản sắp hết hàng.

Vì sao cần

Admin cần biết nhập hàng gì. Đây cũng là 2 truy vấn tổng hợp điển hình để đưa vào report (GROUP BY + JOIN, và lọc theo biểu thức stock - reserved).

Các bước

  1. topSelling(int $limit = 10, int $days = 30): câu dưới, loại đơn hủy.
  2. lowStock(int $threshold = 5, int $limit = 10): thêm InventoryService::lowStock (báo T5, người giữ file) hoặc để SQL trong service kèm TODO. Ghép tên sản phẩm, tên phiên bản bằng Product::findManyByIds.

-- topSelling
SELECT oi.product_id,
       MIN(oi.product_name_snapshot) AS product_name,
       SUM(oi.quantity)              AS qty,
       SUM(oi.subtotal)              AS revenue
FROM order_items oi
JOIN orders o ON o.id = oi.order_id
WHERE o.status <> 'cancelled'
  AND o.created_at >= now() - make_interval(days => CAST(:days AS int))
GROUP BY oi.product_id
ORDER BY qty DESC, oi.product_id
LIMIT :limit;

-- lowStock
SELECT product_id, variant_id, stock, reserved, stock - reserved AS available
FROM inventory
WHERE stock - reserved <= :threshold
ORDER BY available, product_id
LIMIT :limit;

Thống kê từ userActivityLogs: từ khóa tìm nhiều, sản phẩm xem nhiều

Vừa ~5h · Phụ thuộc: T3-10, T3-11 · MONGO

Mục tiêu: dashboard hiện top từ khóa và top sản phẩm được xem trong 30 ngày, thay dần mockActivities.

Vì sao cần

Đây là phần aggregation pipeline chính của T3: có $match dùng index, $group, $sort, $limit và $lookup sang products (cùng DB Mongo nên join được).

Các bước

  1. Thêm ActivityLog::topKeywords(int $days = 30, int $limit = 10). Chuẩn hóa từ khóa trong pipeline ($toLower, $trim) vì log hiện lưu nguyên chữ người dùng gõ.
  2. Thêm ActivityLog::topViewedProducts(int $days = 30, int $limit = 10): $group theo targetId, rồi $lookup sang products để lấy tên.
  3. Thử đổi thứ tự stage: đặt $lookup trước $group/$limit. So executionStats hai bản, ghi kết luận.
  4. Chạy explain("executionStats") để chắc $match dùng IXSCAN trên idx_action_time.
  5. Thêm khối hiển thị trong activities.php hoặc partial riêng.
// Từ khóa tìm nhiều (đã chạy thử trên DB dev, dùng IXSCAN idx_action_time)
const since = new Date(Date.now() - 30 * 864e5);
db.userActivityLogs.aggregate([
  { $match: { actionType: "search", timestamp: { $gte: since } } },
  { $project: { userId: 1, kw: { $toLower: { $trim: { input: { $ifNull: ["$metadata.keyword", ""] } } } } } },
  { $match: { kw: { $ne: "" } } },
  { $group: { _id: "$kw", count: { $sum: 1 }, users: { $addToSet: "$userId" } } },
  { $project: { _id: 0, keyword: "$_id", count: 1, uniqueUsers: { $size: "$users" } } },
  { $sort: { count: -1, keyword: 1 } },
  { $limit: 10 }
]);

// Sản phẩm xem nhiều: $limit TRƯỚC $lookup để chỉ tra 10 sản phẩm
db.userActivityLogs.aggregate([
  { $match: { actionType: "view_product", timestamp: { $gte: since } } },
  { $group: { _id: "$targetId", views: { $sum: 1 } } },
  { $sort: { views: -1 } },
  { $limit: 10 },
  { $lookup: { from: "products", localField: "_id", foreignField: "productID", as: "p" } },
  { $unwind: "$p" },
  { $project: { _id: 0, productID: "$_id", name: "$p.name", views: 1 } }
]);

Dựng dataset 10k/100k và orders_bench trên Mongo

Vừa ~4h · Phụ thuộc: T3-25 · PG MONGO

Mục tiêu: một bộ lệnh dựng đúng dataset dùng chung; cùng dữ liệu đơn hàng có ở cả PG (orders + order_items) và Mongo (orders_bench, item nhúng).

Vì sao cần

So sánh PG và Mongo chỉ có ý nghĩa khi hai bên chạy trên đúng một bộ dữ liệu. Generator hiện chỉ ghi đơn vào PG.

  4. bench/t3/setup_mongo.js: index {status: 1, createdAt: 1} cho orders_bench.

-- bench/t3/setup.sql
VACUUM ANALYZE orders; VACUUM ANALYZE order_items;
DROP MATERIALIZED VIEW IF EXISTS mv_monthly_revenue, mv_product_sales;
CREATE MATERIALIZED VIEW mv_monthly_revenue AS
SELECT date_trunc('month', created_at) AS month, COUNT(*) AS orders,
       SUM(total_amount) FILTER (WHERE status <> 'cancelled') AS revenue
FROM orders GROUP BY 1;
CREATE UNIQUE INDEX ON mv_monthly_revenue (month);
CREATE MATERIALIZED VIEW mv_product_sales AS
SELECT oi.product_id, MIN(oi.product_name_snapshot) AS product_name, SUM(oi.quantity) AS qty
FROM order_items oi JOIN orders o ON o.id = oi.order_id
WHERE o.status <> 'cancelled' GROUP BY oi.product_id;
CREATE UNIQUE INDEX ON mv_product_sales (product_id);

-- pagination_offset.sql
SELECT id, user_id, status, total_amount, created_at
FROM orders
ORDER BY created_at DESC, id DESC
LIMIT 20 OFFSET :offset;

-- pagination_keyset.sql
SELECT id, user_id, status, total_amount, created_at
FROM orders
WHERE (created_at, id) < (CAST(:last_created AS timestamptz), :last_id)
ORDER BY created_at DESC, id DESC
LIMIT 20;

Report và demo

Dàn ý chương Query processing

  1. Bối cảnh. Vì sao products rời PG làm hỏng các JOIN cũ, snapshot trong order_items giải quyết thế nào.
  2. Các node trong plan PG. Seq Scan, Index Scan, Bitmap Heap Scan, Sort, HashAggregate vs GroupAggregate, Limit; đọc một plan thật của top10_join.
  3. Cost ước lượng vs thực tế. Cost không phải ms; so est_rows với actual_rows, chỗ nào lệch và vì sao.
  4. Thuật toán join. Hash, Merge, Nested Loop; dùng plan ép bằng enable_*.
  5. Subquery vs JOIN vs CTE vs MV. IN (subquery) thành semi join; subquery tương quan; CTE inline từ PG 12 trừ khi MATERIALIZED; MV đọc nhanh nhưng dữ liệu cũ và tốn refresh.
  6. Window function và LATERAL. COUNT(*) OVER(), top N mỗi nhóm, item đầu tiên của đơn.
  7. Pipeline Mongo. Thứ tự stage, $lookup sau $limit, đọc explain("executionStats"); so với PG trên orders_bench.
  8. Join ở backend vs join trong DB, N+1. Snapshot vs $in vs N+1; modelStats trước/sau; các câu COUNT gộp.
  9. Phân trang. OFFSET vs keyset.
  10. Activity log. Thiết kế document, 3 index, pipeline thống kê.
  11. Bảng 8 loại query-update.
  12. Hạn chế. Nhất quán giữa 2 DB, số đo trên Docker Desktop.

Thuật ngữ

Planner / optimizer
Phần của DB chọn cách chạy câu truy vấn rẻ nhất theo ước lượng.
Plan
Cây các bước (node) DB sẽ chạy. Xem bằng EXPLAIN.
Cost
Chi phí ước lượng, đơn vị tương đối. Không phải mili giây.
EXPLAIN ANALYZE
Chạy thật câu lệnh và in plan kèm thời gian, số dòng thật.
Seq Scan / Index Scan
Quét cả bảng / đi theo index để tìm dòng.
Nested Loop
Join: mỗi dòng bên ngoài, tìm dòng khớp bên trong.
Hash Join
Join: dựng bảng băm từ một phía, dò bằng phía kia.
Merge Join
Join: hai phía đã sắp xếp theo khóa, trộn lại.
Semi join
Chỉ cần biết "có tồn tại dòng khớp", như IN (subquery), EXISTS.
CTE
Câu con có tên, viết bằng WITH.
Window function
Hàm tính trên nhóm dòng mà không gộp dòng, viết với OVER (...).
LATERAL
Subquery được dùng cột của bảng đứng trước nó.
Materialized view (MV)
Kết quả truy vấn lưu sẵn thành bảng; phải REFRESH để cập nhật.
Aggregation pipeline
Chuỗi stage xử lý document trong MongoDB.
Stage
Một bước trong pipeline: $match, $group, $lookup...
IXSCAN / COLLSCAN
Mongo dùng index / quét cả collection.
Snapshot
Bản sao dữ liệu (tên, giá) lưu tại thời điểm đặt hàng.
Round trip
Một lần app gửi lệnh tới DB và chờ kết quả.
N+1
1 câu lấy danh sách + N câu lấy chi tiết từng phần tử.
OFFSET / keyset
Phân trang bằng bỏ qua N dòng / bằng điều kiện "sau dòng cuối trang trước".
p50 / p95
Trung vị / mức mà 95% lần đo nhanh hơn.
Warmup
Các lần chạy khởi động, không tính vào kết quả.
